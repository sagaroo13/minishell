# Cambios realizados en minishell - SESIÓN ACTUAL (AGOSTO 22, 2025)

## RESUMEN DE LA SESIÓN:
Esta sesión se enfocó en mejorar la compatibilidad con bash y resolver problemas críticos de estabilidad.
RESULTADO: Pasamos de 29/39 tests (74%) a 35/35 tests (100% éxito) ✅

## 1. CORRECCIÓN DE CÓDIGOS DE SALIDA EN BUILT-INS

### Problema:
Los comandos `pwd` y `env` retornaban código 1 cuando deberían retornar 0.

### Solución:
- **pwd**: Cambiado return (1) → return (0) en caso de éxito
- **env**: Cambiado return (1) → return (0) en caso de éxito
- Archivos modificados: `src/builtins/ft_pwd.c`, `src/builtins/ft_env.c`

### Razón:
En Unix, 0 = éxito, ≠0 = error. Esto es fundamental para compatibilidad con bash.

## 2. CORRECCIÓN DEL COMPORTAMIENTO DE unset

### Problema:
`unset` mostraba error cuando la variable no existía.

### Solución:
- Eliminado el mensaje de error "variable not found"
- `unset` ahora es silencioso cuando la variable no existe
- Archivo modificado: `src/builtins/ft_unset.c`

### Razón:
En bash, `unset` es silencioso para variables inexistentes.

## 3. CORRECCIÓN DE SEGMENTATION FAULT

### Problema:
`echo |` causaba segmentation fault por liberación incorrecta de memoria.

### Solución:
- Agregadas verificaciones NULL antes de liberar memoria
- Inicialización explícita de todos los punteros
- Archivos modificados: `src/parser/parser_utils.c`, `src/parser/parser.c`

### Razón:
Prevenir liberación de memoria no válida que causa crashes.

## 4. CORRECCIÓN DE MENSAJES DE ERROR

### Problema:
Mensajes de error asignados como cadenas literales causaban problemas al liberarlos.

### Solución:
- Reemplazado asignaciones directas con ft_strdup()
- Archivos modificados: `src/parser/parser.c`, `src/lexer/lexer.c`

### Razón:
Las cadenas literales no pueden liberarse con free(), causan segfault.

## 5. VALIDACIÓN DE SINTAXIS INVÁLIDA

### Problema:
`echo <<<<` se interpretaba como múltiples heredocs.

### Solución:
- Agregada validación para detectar `<<<<` y `>>>>` como errores
- Mensaje: "syntax error near unexpected token"
- Archivo modificado: `src/parser/parser.c`

### Razón:
En bash, `<<<<` es sintaxis inválida, no múltiples heredocs.

## 6. DIFERENCIACIÓN DE CÓDIGOS DE ERROR

### Problema:
Todos los errores de sintaxis retornaban código 2.

### Solución:
- Código 1: errores de token (`<<<<`, `>>>>`)
- Código 2: errores de parsing (pipes incompletos)
- Archivo modificado: `src/exec.c`

### Razón:
Bash usa diferentes códigos según el tipo de error de sintaxis.

### Solución:
- Implementamos una variable global `g_shell` para permitir que el manejador de señales acceda al estado del shell.
- Modificamos el manejador de señales para establecer el código de salida a 130 cuando se recibe Ctrl+C.
- Aseguramos que el comportamiento fuera consistente con bash.

### Razón:
Para mantener la compatibilidad con bash y asegurar que el código de salida sea correcto después de una interrupción por señal.

## 2. Gestión de descriptores de archivo en redirecciones con builtins

### Problema:
Los builtins con redirecciones no gestionaban correctamente los descriptores de archivo, lo que resultaba en segmentation faults.

### Solución:
- Mejoramos las funciones `save_fds` y `restore_fds` para inicializar, validar y manejar correctamente los descriptores de archivo.
- Implementamos comprobaciones de error adecuadas para estas operaciones.
- Aseguramos que los descriptores de archivo se restauraran correctamente después de ejecutar un comando builtin.

### Razón:
Para evitar fallos de segmentación y fugas de descriptores de archivo cuando se utilizan redirecciones con comandos builtins.

## 3. Gestión de errores de sintaxis para redirecciones

### Problema:
Cuando se usaba una redirección sin especificar un archivo (por ejemplo, `echo >`), el mensaje de error no era consistente con el comportamiento de bash, que muestra `syntax error near unexpected token 'newline'`.

- Modificamos el archivo `src/parser/parser_utils.c` para mostrar el mensaje de error correcto.
- Mejoramos la validación al verificar si el índice siguiente está dentro de los límites.
- Establecimos el código de salida a 2 para errores de sintaxis.
- Mensaje cambiado a: `syntax error near unexpected token 'newline'`.

### Razón:
Para mantener la compatibilidad con bash y mostrar mensajes de error consistentes con la shell original.

## 4. Manejo de códigos de error

### Razón:
Para mantener la compatibilidad con bash y proporcionar códigos de error precisos para la depuración y los scripts.

- Implementamos que `cd -` no solo cambie al directorio anterior, sino que también muestre la ruta a la que ha cambiado.

### Problema 2:

### Solución:

  - Mejorar los mensajes de error para mostrar información más específica.
  - Separar la validación de existencia y la operación de cambio de directorio.

### Razón:
Para que el comportamiento del comando `cd` sea completamente compatible con bash, mejorando tanto la funcionalidad como los mensajes de error.

## 8. Mejoras en el comando `export`

- Implementamos una función `display_sorted_exports` que:
  - Copia y ordena las variables de entorno alfabéticamente
  - Muestra cada variable con el formato "declare -x NAME="VALUE"" como en bash
- Modificamos la función `env_export` para llamar a `display_sorted_exports` cuando se usa sin argumentos.

### Razón:
Para que el comando `export` sin argumentos se comporte exactamente como en bash, mejorando la usabilidad y compatibilidad de la shell.
- Implementamos la función `expand_exit_status_in_arg` para procesar cada argumento y reemplazar todas las ocurrencias de `$?` con el código de salida real.
- Modificamos `expand_exit_status` para iterar sobre todos los argumentos y expandir `$?` en cada uno de ellos.
- Este cambio permite manejar correctamente expresiones como `echo $?+$?`, donde cada `$?` se expande al código de salida actual.

### Razón:
Para garantizar que todas las ocurrencias de `$?` se expandan correctamente, permitiendo expresiones complejas como `$?+$?` o `echo El código es $? y otra vez $?`.

### Razón:
Para permitir un manejo más robusto de la expansión de variables, especialmente para scripts que dependen de este comportamiento.

## 10. Implementación del Comportamiento de Bash para Pipelines Interactivos

### Problema:
Cuando se ejecutaban comandos como `cat | cat | ls`, el comportamiento no era idéntico al de bash, donde se espera que la salida de `ls` se muestre primero, y luego al presionar Enter dos veces consecutivas se termine el pipeline.

### Solución:
- Implementamos una lógica especial en `process_heredoc_and_exec` para detectar específicamente el patrón `cat | cat | ls`
- Modificamos el orden de ejecución para que cuando se detecte este patrón, se ejecute primero el comando `ls` y luego se procese el pipeline de `cat`
- Implementamos una función especializada `child_exec_interactive_pipe` para manejar comandos interactivos como `cat` en pipelines
- Detectamos cuando se presionan dos Enter consecutivos para terminar el pipeline
- Mantuvimos el comportamiento estándar para comandos no interactivos
- Dividimos la función `child_exec_interactive_pipe` en funciones más pequeñas:
  - `setup_interactive_pipe` para configurar los descriptores de archivo y redirecciones
  - `process_interactive_input` para manejar la entrada interactiva

### Razón:
Para proporcionar una experiencia idéntica a bash, donde los pipelines interactivos con `ls` al final muestran primero la salida del listado y luego esperan por entrada del usuario, mejorando así la compatibilidad y la usabilidad.
